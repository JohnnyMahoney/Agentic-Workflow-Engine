# Discovery acceptance and recovered failures

Human-assisted runs additionally require matching intervention audit records.
Compilation preflight and Builder verify any human changes against the approved
trusted blocker policy; manual business actions are not executable evidence.
See [Discovery handoff](discovery-handoff.md) for the narrow proof and its limits.

The pipeline is unchanged. Acceptance is staged:

1. Discovery ends and saves all actions, including failures.
2. Deterministic admission establishes eligibility for Compilation.
3. Separate Claude Compilation proposes a candidate using successful actions.
4. Builder validates action coverage, outputs and final semantic checkpoints.
5. Only a validated artifact can proceed to deterministic Replay.

`eligible-for-compilation` explicitly has goalVerification pending. It is not a
successful business result, accepted artifact or proof of Replay.

## Initial safe recovery rule

The only admitted failure class is `FORM_INPUT_REJECTED` in the driver guard that
precedes fill/selectOption and all potentially mutating browser calls. Require:

- normal model termination with corroborating audit when provided;
- original consecutive action indices and a reached entry URL;
- typed beforeDispatch metadata, or the specific legacy driver diagnostic in the
  companion audit for old recordings;
- identical before/after snapshots (an additional conservative requirement);
- a uniquely identifiable failed ref in the recorded DOM;
- a successful form_input on the same frame/node and root URL, bound to an explicit
  request input, before another interaction (reads and waits may intervene);
- subsequent successful textual observations.

New runs preserve failed target refs without input values, record failure phase/code,
and separately record modelCompleted. They retain the old clean-run completed flag
for compatibility. The loop, browser behavior, instructions and limits are unchanged.

For legacy evidence, `events.jsonl` and `summary.json` in the evidence directory
must corroborate normal termination, failure count, run identity and action count.
The exact diagnostic is a known error generated by our own driver guard, not an
arbitrary UI message. Both sidecars are hashed in the admission report. Source
evidence is never rewritten, filtered or reindexed.

Unknown dispatch, failed clicks, state changes or uncertain side effects reject
admission. Equal DOM alone cannot show that no server-side mutation occurred.
Normal termination or a later success does not resolve these cases. Additional
failure classes need explicit safety rules; no general reconciler is implemented.

## Builder rules

Failed actions are retained in compilation audit data and omitted from the executable
artifact. They cannot be referenced by stepEvidence or checkpointEvidence. Successful
navigate/click/input actions still need complete chronological executable coverage.

A recovered run requires Capability v2.1, declared validated outputs and semantic
final checkpoints using input references for every supplied input. Each condition
must match its successful recorded state and pass existing intermediate-state
validation. A model's final response alone is insufficient.

Artifacts with an unsupported goal or insufficient evidence are rejected. The
checks verify the explicit output/checkpoint contract, not arbitrary natural-language
meaning or future locator stability. Fresh-session Replay is still a separate test.

## Reports and retry

The CLI reports `recorded-for-compilation` with goalVerified false after admission.
Compilation saves `discovery-admission.json`; rejected admission also saves a
compilation-error.json. Builder saves `discovery-acceptance.json` only after its
candidate validations pass, listing excluded failed action indices and audit proof.

```powershell
npm.cmd run capability:compile -- --evidence <saved-discovery>/discovery-v2.json --policy <policy.json> --out <new-compilation-directory>
npm.cmd run capability:replay -- --artifact <new-compilation-directory>/artifact.json --input memberId=M-1010 --input accountType=Youth --policy <policy.json> --out <new-replay-directory>
```

Keep original sidecars alongside legacy evidence; without them, untyped legacy
failures fail closed. No new Discovery is required when existing evidence satisfies
admission and Builder. Test 6's actual outcome and limits are in the
[evidence index](../evidence/discovery-recovery/README.md).

Compilation token limits are independent of admission. A truncated response is
rejected with `COMPILATION_INCOMPLETE`; no partial JSON is repaired or accepted.
`CLAUDE_COMPILATION_MAX_TOKENS` configures a bounded 1000–32000 output-token budget
(default 10000), recorded as maxTokens in compilation-request.json. For a long
recording, set `$env:CLAUDE_COMPILATION_MAX_TOKENS='20000'` before retrying only
Compilation in a fresh directory. This never changes Discovery or validation rules.
